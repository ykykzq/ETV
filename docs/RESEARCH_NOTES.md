## 程序验证

程序验证针对显式前置条件所覆盖的全部状态，建立程序与规格之间的数学关系。Hoare 最初的公理化方法使用前置条件、程序语句和后置条件来表达这一关系；循环还需要不变式，而完全正确性还需要递减变式。参见 [Hoare, 1969](https://doi.org/10.1145/363235.363259)。

对本工程而言，相关规格是关系型而非一元规格：

```text
P(lhs_state, rhs_state)
  => Defined(lhs) and Defined(rhs)
  and ObservableMemory(Exec(lhs)) = ObservableMemory(Exec(rhs))
```

`P` 包含 ABI 角色、形状/步长 specialization、启动配置对应关系、定义性以及 no-alias 事实。求解器结果仅在已编码语义和这些前提下才有意义。

## 等价性验证与翻译验证

一般的程序等价性问题不可判定。翻译验证通过检查某次编译或优化产生的一对具体源程序/目标程序来缩小问题，而不是证明编译器对所有程序都正确。原始表述参见 [Pnueli 等](https://link.springer.com/chapter/10.1007/BFb0054170)。

[Alive2](https://web.ist.utl.pt/nuno.lopes/pubs.php?id=alive2-pldi21) 展示了编译器 IR 上的实用模式：符号执行、显式 IR/内存语义、SMT、有界循环处理、考虑 refinement 的定义性，以及具体反例。有界分析可能遗漏边界之外的错误，因此界限必须成为证明结论的一部分。

ETV 遵循这一原则：

- 验证一个固定程序对及其 specialization；
- 询问是否存在差异；
- 只有通过穷举或代数推理封闭否定后的证明义务时，才返回 `PROVED`；
- 为 `DISPROVED` 返回见证；
- 对不受支持或耗尽资源的证明尝试保留 `UNKNOWN`。

## 等式饱和

经典等式饱和不会破坏性地选择单一重写顺序，而是持续加入等式、让共享表示达到饱和，最后再从中选择或比较已表示的项。参见 [Tate 等，2009](https://cseweb.ucsd.edu/~lerner/papers/popl09.html)。

E-graph 表示一个同余关系：如果两个子项相等，那么在重建后，使用相同父操作符的父项也相等。[egg](https://arxiv.org/abs/2004.03082) 通过摊销重建和 e-class 分析让等式饱和变得实用；[egglog](https://arxiv.org/abs/2304.04332) 则将其与 Datalog 风格的事实和关系结合。

关键的健全性要求位于数据结构之外。只有由以下原因触发时，e-class 合并才可信：

1. 语法哈希驻留；
2. 同余；
3. 预先验证的等式；
4. 显式列出的可信公理。

ETV 会记录每一次合并的原因，并在使用当前规则前通过 Z3 验证它们。采样结果和语言模型建议永远不会直接合并 e-class。

## 用户指定的参考资料

### 对 AI 生成的 GPU Kernel 进行形式化验证

[Gimlet Labs 文章](https://gimletlabs.ai/blog/formally-verifying-ai-generated-kernels)把 PyTorch 和 TTIR 降低到共同的 TensorAlgebra DAG，从 `tt.store` 开始反向遍历，分解高层操作、将输出元素标量化，然后询问 Z3 是否存在差异。该方法使用精确实数值和有界归约展开，并明确报告证明、反例或未知。

对 ETV 的启发：

- 以可观察 store 作为根节点；
- 在有限化输出索引的同时保持值为符号形式；
- 固定 specialization 使完整 lane 枚举变得可行；
- 必须明确标注精确实数浮点语义，不能将其与 GPU 位级语义混淆；
- 不能把有界归约证据提升为参数化归约定理。

### 深度学习算子的验证式提升

[Zhan 等，2024](https://arxiv.org/abs/2412.20992)结合符号执行、语法引导综合、Hoare 风格不变式、SMT 验证和 e-graph 简化，把低层 Triton 算子提升为数学摘要。论文还报告了重要限制：需要手工标注形状/线程、公式语言无法表达部分操作（包括掩码）、使用精确实数而非浮点语义，以及求解器可能返回 UNKNOWN。

对 ETV 的启发：

- Semantic TTIR 是类型化证明 IR，而不是对原始文本做重写；
- 标注应成为显式 PairSpec 事实，并出现在报告中；
- 掩码、地址和内存必须保持为一等对象，而不能被纯数学摘要抹去；
- 等式饱和应在语义恢复之后使用，而不能充当解析器。

### Emerge：验证大型模型的实现等价性

[Zhan 等，2026](https://arxiv.org/abs/2603.21851)构建联合 e-graph，根据执行值推断候选节点关系，从共享抽象前沿综合桥接规则，使用适用的最强方法验证每条候选规则，重建同余关系，并定位第一个无法匹配的前沿。

对 ETV 的启发：

- 在证明可观察根节点前，先证明节点/证明块级关系；
- 仅激活与未匹配计算切片相关的规则族；
- 将事实与等价类分开；
- 把角色、布局和内存对象视为共享前沿；
- 保留失败定位和证据等级。

Emerge 允许经过经验验证的不透明规则参与后续合并。ETV MVP 有意采用更严格的本地策略：经验证据可以指导未来的候选生成，但不能用于证明程序对。

## 其他 GPU Kernel 研究证据

[VOLTA](https://arxiv.org/abs/2511.12638)通过符号求值验证一类结构化 PTX GPU kernel，检查竞争/死锁，在实数张量值上推理，并证明不同调度之间的合流性。它进一步支持两项设计决策：显式限制支持的程序类别，并把无竞争性作为证明义务，而不是假设算术匹配就已足够。

## 对压缩包中模糊与冲突之处的处理

1. **浮点语义。** 早期 add 材料把浮点数描述为普通整数/位向量值；较晚的系统设计则一致选择数学意义上的 `ABSTRACT_FLOAT`。实现遵循较晚的设计。
2. **raw TTIR 解析器。** 设计正确地拒绝正则表达式解析，并建议使用 Triton 已注册方言的 MLIR 解析器。仓库中没有 TTIR 文件或 Triton 运行时，当前 Apple Silicon 环境也无法验证该 Linux/CUDA 适配器。因此，raw 提升被明确放在 MVP 信任边界之外，而没有用脆弱的文本解析来假装实现。
3. **egglog 与本地引擎。** 对关系事实和循环而言，egglog 是长期建议。MVP 的本地计算专用 e-graph 足以封闭 add 证明并暴露每次合并；当 M3 需要循环/定义域关系时应重新评估该决策。
4. **形式化规则与经验规则。** 动态相等只是候选证据，不是证明。MVP 只准入由 Z3 证明的抽象实数规则。
5. **循环。** 把循环编码为 `theta` 可以避免展开，但这本身不是证明。覆盖性、唯一性、单位元、地址以及归纳/归约顺序证明义务仍未实现，在 M3 前应返回 `UNKNOWN`。
